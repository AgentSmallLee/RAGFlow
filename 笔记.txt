==================== RAG 项目开发笔记 ====================
整理日期：2026-08-25

==========================================================
一、conda 环境为什么新终端不生效？
==========================================================

原因：conda 环境激活是"会话级别"的——在哪个终端执行 conda activate，
      就只在那个窗口生效。新开的终端会默认使用 base 环境或系统 Python。

解决方法：
  1. 手动激活：conda activate agent-project（最常用）
  2. 配置别名：在 ~/.zshrc 里加 alias，一键 cd + 激活
  3. VS Code：选好 Python 解释器后，集成终端会自动激活
  4. conda run -n agent-project xxx（不激活环境也能跑命令）

==========================================================
二、Embedding 和 LLM 要不要分开配置 API Key 和 Base URL？
==========================================================

答案：要！

原因：Embedding 模型和聊天模型完全可能来自不同的服务商。
      比如聊天用 DashScope 通义千问，向量化用 SiliconFlow 的 BGE-M3。

项目中的做法：
  - LLM 配置：       LLM_API_KEY / LLM_BASE_URL / LLM_MODEL
  - Embedding 配置： EMBEDDING_API_KEY / EMBEDDING_BASE_URL / EMBEDDING_MODEL
  - 两者完全独立，互不干扰

代码位置：
  - 定义在 config/settings.py
  - 真实值写在 .env 文件里

==========================================================
三、配置放 settings.py 还是 .env 文件？
==========================================================

结论：
  - 敏感信息（API Key、密码等）→ 放 .env 文件
  - 非敏感配置（chunk_size、top_k 等）→ 可以放 settings.py 当默认值

原因：
  - settings.py 会被提交到 git，写死密钥有泄露风险
  - .env 加入 .gitignore，永远不会被提交
  - 非敏感配置留默认值方便新人上手，也能被 .env 覆盖

工作原理：
  .env 文件 → pydantic-settings 自动读取 → settings 对象
  settings.py 里配置了 SettingsConfigDict(env_file=".env")
  .env 里的值优先级高于 settings.py 的默认值

==========================================================
四、settings.py 的字段名和 .env 的变量名怎么对应？
==========================================================

规则：名称必须一致，只是大小写不同。

具体说：pydantic-settings 会自动把 settings.py 里的字段名转成大写，
      然后去环境变量（包括从 .env 加载的）里找同名的值。

例子：
  settings.py 字段名    .env 环境变量名
  ------------------   ----------------
  llm_api_key     ↔    LLM_API_KEY
  llm_base_url    ↔    LLM_BASE_URL
  llm_model       ↔    LLM_MODEL
  embedding_model ↔    EMBEDDING_MODEL
  chunk_size      ↔    CHUNK_SIZE
  top_k           ↔    TOP_K

注意：
  - 不区分大小写（配置了 case_sensitive=False）
  - 但名字本身的内容必须一样，比如 llm_api_key 写成 llm_key 就匹配不上

高级用法（暂时用不到）：
  如果想让 .env 里的名字和代码字段名不一样，可以用 Field(alias="...")

==========================================================
五、实际开发中 requirements.txt 常见吗？
==========================================================

答案：非常常见，是 Python 项目标配。

常见的几种做法：

  1. 单个 requirements.txt
     → 小型项目、个人项目、演示项目

  2. 生产/开发分离
     requirements.txt       生产必需依赖
     requirements-dev.txt   开发/测试额外依赖（pytest、black、mypy 等）

  3. requirements/ 目录细分
     base.txt   基础依赖
     dev.txt    开发依赖（继承 base）
     prod.txt   生产依赖（继承 base）

  4. 现代方式：pyproject.toml
     配合 poetry / uv 等工具，依赖和项目元信息都在这里

  5. 锁定版本文件
     requirements-lock.txt 或 poetry.lock
     锁定精确版本，保证不同环境装出来完全一致

当前项目：单个 requirements.txt，合适。
项目变大后可以考虑拆分生产/开发。

八、更换 Embedding 模型后要做哪些操作？
==========================================================

按重要程度分三层：必做 → 推荐 → 可选。

【🔴 必做（不做就跑不起来）】

1. 重建向量库（最最重要）
   不同模型的向量维度、语义空间完全不同，不能混用。
   操作：删除旧向量库 → 重新运行 build_index.py
   命令：rm -rf data/vector_db && python build_index.py

2. 修正代码中的模型配置
   - 后端适配：确认调用方式正确（OpenAI 兼容 / DashScope SDK / 本地模型）
   - API Key / Base URL：确认凭证和端点对应正确

3. 调整相似度阈值
   不同模型的分数分布差异很大，别用同一套阈值。
   常见模型分数参考：
     - OpenAI text-embedding-3：相关 0.7~0.9，阈值建议 0.7~0.8
     - 通义 text-embedding-v3： 相关 0.6~0.8，阈值建议 0.5~0.6
     - bge-m3：                相关 0.4~0.7，阈值建议 0.3~0.5
   方法：用几个典型查询实际跑一下，看分数分布再定阈值。

【🟡 推荐做（提升效果）】

4. 验证检索质量
   用一组有标准答案的查询测试，检查：
     - 召回率：相关文档有没有被检索出来？
     - 排序质量：最相关的是不是排在前面？
     - 误检率：不相关的会不会被错误命中？

5. 适配模型的特殊用法
   有些模型有特定的最佳实践：
     - BGE 系列：查询时要加 instruction 前缀
       中文："为这个句子生成表示以用于检索相关文章："
     - Multilingual-E5：查询加 "query: "，文档加 "passage: "
     - OpenAI / 通义 系列：不需要特殊前缀

6. 调整 chunk 大小
   不同模型对文本长度敏感度不同，可以微调 chunk_size 和 chunk_overlap。

【🟢 可选（进阶优化）】

7. 评估并更新系统参数
   - top_k：返回多少个候选（一般 3~10）
   - 距离度量：cosine（推荐） vs l2 vs ip（内积）

8. 加入 Reranker 二次精排
   首检质量不够时，加 reranker（bge-reranker、Cohere Rerank 等）效果提升明显。

9. 记录版本和基线
   - 记录模型名、版本、建库时间
   - 保存评测查询和结果作为 baseline，换模型时对比

【📋 速查清单】
  □ 删除旧向量库
  □ 更新代码中的模型维度
  □ 确认 API Key / Base URL / 调用方式
  □ 重新运行 build_index.py
  □ 跑几个查询看分数范围
  □ 调整 similarity_threshold
  □ 验证检索准确性（相关排前面、不相关过滤掉）
  □ 跑测试用例

【实战对比：bge-m3 vs text-embedding-v3】
  指标              bge-m3 (SiliconFlow)    text-embedding-v3 (DashScope)
  ---------------  -----------------------  ----------------------------
  检索准确性        ❌ 差（排序混乱）        ✅ 好（准确命中）
  区分度           ❌ 差（不相关也 0.6+）   ✅ 好（不相关 < 0.4）
  维度             1024                     1024
  推荐指数          ⭐                       ⭐⭐⭐⭐⭐

十、RAG 检索不到结果的常见原因排查清单
==========================================================

现象：文档已经切分、向量化、入库了，但用户提问后检索不到任何结果，
      或者返回"未找到相关参考资料"。

排查思路：从最常见、最容易验证的原因开始，从上到下逐一排除。

【🔴 第一类：向量库根本没东西 / 连不上（最常见）】

1. 向量库是空的
   现象：初始化时 count = 0
   排查：启动时看日志里的"已有文档数"是不是 0
   原因：没跑 build_index.py，或者文档目录是空的
   解决：先确认文档存在，再重新建库

2. 向量库路径不对
   现象：chat.py 和 build_index.py 用了不同的 vector_db_path
   排查：打印两边的 settings.vector_db_full_path 对比
   原因：运行目录不同导致相对路径解析不一样
   解决：用绝对路径，或者确保在项目根目录运行脚本

3. 集合名称不匹配
   现象：建库用了 collection A，查询用了 collection B
   排查：确认两边的 collection_name 一致
   原因：.env 改了配置但只重跑了一边

4. 换了 embedding 模型但没重建向量库
   现象：检索分数极低，或者维度报错
   原因：不同模型的向量空间完全不同，不能混用
   解决：rm -rf data/vector_db && python build_index.py
   （这是非常高频的坑！）

【🟠 第二类：检索被阈值过滤掉了（非常常见）】

5. 相似度阈值设置太高
   现象：原始检索有结果，但过滤后为 0
   排查：打印 similarity_search_with_score 的原始分数
   原因：阈值 > 所有结果的相似度
   解决：
     - 先把阈值设低（比如 0.1）确认能搜到，再逐步调高
     - 不同模型分数范围不一样，不能用同一套阈值
     - 参考：OpenAI 0.7~0.8，通义 v3 0.5~0.6，bge-m3 0.3~0.5

6. 分数转换公式错了
   现象：转换后的相似度分数普遍偏低
   原因：
     - Chroma 默认返回"距离"（越小越相似），不是"相似度"
     - 用了错误的转换公式（比如 L2 距离当成 cosine 距离转）
   对应关系：
     - cosine 距离 → 相似度 = 1 - distance
     - l2（欧氏距离平方）→ 相似度 = 1 / (1 + distance)
   排查：打印原始距离分数，对比转换后的相似度

7. 距离度量和模型不匹配
   现象：分数分布奇怪，排序不合理
   原因：Chroma 默认 L2 距离，但很多 embedding 模型用余弦相似度更好
   解决：新建集合时指定 collection_metadata={"hnsw:space": "cosine"}
   注意：已有集合不能改距离度量，必须删了重建

【🟡 第三类：Embedding 模型问题】

8. 查询和文档用了不同的 embedding 模型
   现象：检索结果完全不相关，分数异常
   原因：建库时用模型 A，查询时用模型 B
   排查：打印 build_index 和 chat 时的 embedding.model 对比

9. 查询时忘了加模型专用前缀
   现象：BGE / E5 等模型检索质量差，排序不对
   原因：这些模型训练时查询和文档用了不同的前缀
   对应前缀：
     - BGE 中文："为这个句子生成表示以用于检索相关文章："
     - BGE 英文："Represent this sentence for searching relevant passages: "
     - E5 系列：查询加 "query: "，文档加 "passage: "
     - OpenAI / 通义：不需要前缀

10. 向量模型本身质量差 / 不适合中文
    现象：所有查询的 top1 都是同一篇文档，区分度极低
    原因：
      - 某些第三方 API 的 bge-m3 实现有问题
      - 模型没在中文语料上微调过
    解决：换质量更好的模型（如通义 text-embedding-v3）

11. 文档向量生成失败（静默失败）
    现象：向量库里有记录但内容为空，或者全是零向量
    原因：API 调用失败但被 try-except 吞掉了
    排查：检查向量库中文档内容是否正常，向量是不是全零

【🟢 第四类：文本切分问题】

12. chunk 太大，关键信息被稀释
    现象：能搜到但排不到前面
    原因：一个 chunk 里内容太多，主题不聚焦，向量"平均化"了
    解决：调小 chunk_size（比如从 1000 改到 500）

13. chunk 太小，缺少上下文
    现象：搜不到完整答案
    原因：关键概念被切分到不同 chunk 里
    解决：调大 chunk_size，增加 chunk_overlap

14. 文档内容本身没有答案
    现象：最相关的文档也答非所问
    原因：知识库本来就没覆盖这个话题
    解决：属于正常现象，补充相关文档即可

【🔵 第五类：其他奇怪问题】

15. Embedding 调用了流式接口 / 返回格式不对
    现象：向量维度异常（比如变成 1 维）
    排查：打印 len(embedding.embed_query("test")) 看维度

16. 元数据过滤条件写错了
    现象：加了 filter 后搜不到，去掉 filter 就能搜到
    原因：filter 条件写错，或者元数据字段名不对
    排查：先不加 filter 确认有结果，再逐步加过滤条件

17. 多语言 / 编码问题
    现象：中文查询搜不到中文文档
    原因：某些 embedding 对中英文混合处理不好
    排查：用纯英文查询试试，对比结果

【📋 快速排查步骤（按顺序来）】
  1. 确认向量库不为空（count > 0）
  2. 确认建库和查询用的是同一个模型
  3. 把 similarity_threshold 调到 0.1，看有没有结果
     → 有结果：阈值太高，调回去
     → 没结果：继续往下查
  4. 打印原始相似度分数，看分数分布
  5. 检查距离度量类型（cosine 还是 l2）和分数转换公式
  6. 直接调用 embedding，验证向量维度是否正常
  7. 检查 chunk 内容是否正常（不是空的）
  8. 换一个简单查询试试（比如直接用文档标题当查询）

【💡 经验总结】
  - 90% 的"检索不到"问题，都是前 3 个原因（空库/阈值太高/换模型没重建）
  - 排查时先把阈值调到最低，确认"能搜到"，再逐步调优
  - 打印原始分数是最快的定位方法，分数一出来基本就知道问题在哪
  - 换模型必重建库，这是铁律

==========================================================
十一、RAG 检索不到时，线上真实系统怎么处理？
==========================================================

当前项目的做法：检索不到就直接返回"抱歉，未找到相关参考资料，无法回答此问题"。
这是最保守、最简单的做法，但线上真实系统通常不会这么粗暴。

下面是从"简单"到"复杂"的常见处理策略，可以根据产品需求选择。

【🔵 策略 1：直接告知无法回答（当前实现）】

做法：检索不到相关文档时，直接告诉用户"无法回答"。
代码位置：rag_chain.py 的 query 方法里，if not retrieved_docs 分支。

优点：
  - 实现最简单
  - 不会产生幻觉（胡说八道）
  - 响应快，不用调 LLM

缺点：
  - 体验差，用户感觉系统"很笨"
  - 有些问题其实知识库有相关内容，只是检索没命中
  - 用户不知道该怎么调整问题

适用场景：
  - 对准确性要求极高（如医疗、法律）
  - 内部工具，用户能接受
  - MVP 阶段，先跑通再说

【🟢 策略 2：交给 LLM 判断，让 LLM 说"不知道"】

做法：不做代码层面的拦截，即使检索结果很少/分数很低，也把上下文
      丢给 LLM，靠 system prompt 约束 LLM"没有答案就说不知道"。

关键 Prompt：
  "如果参考资料中没有相关信息，请明确说明无法回答，不要编造内容。"

优点：
  - 比硬编码更灵活，LLM 能判断"虽然文档不直接相关但能推断"
  - 实现简单，写好 Prompt 就行

缺点：
  - 依赖 LLM 的听话程度，小模型可能还是会胡说
  - 还是会调 LLM，花 token 钱

当前项目的 Prompt 里其实已经写了这条规则（prompt_builder.py 第 19 行），
但代码层面又做了一层硬拦截，相当于"双保险"。

【🟡 策略 3：模糊命中，给出可能相关的内容】

做法：检索不到高置信度的结果时，降低阈值返回一些"可能相关"的文档，
      告诉用户"没有完全匹配的，但以下内容可能有帮助"。

实现方式：
  - 设置两档阈值：高阈值（确定相关）+ 低阈值（可能相关）
  - 高阈值没命中时，用低阈值再查一次
  - 回答开头加免责声明："未找到完全匹配的内容，以下信息供参考"

优点：
  - 体验好，用户有"获得感"
  - 很多时候用户的问题只是表述不同，低阈值反而能命中
  - 实现成本不高

缺点：
  - 可能会误导用户（给了不相关的内容）
  - 需要多维护一个阈值

【🟠 策略 4：引导用户换个问法 / 给出建议问题】

做法：检索不到时，不直接说"不会"，而是给出引导。

常见引导方式：
  - "您可以尝试换个关键词，比如 XXX"
  - "目前知识库覆盖了以下话题：A、B、C，您想了解哪个？"
  - "您的问题是不是想问 XXX？（给出几个候选问题）"

进阶做法：用 LLM 根据用户问题生成几个"改写后的问题"，再检索一次。
这叫 "Query Rewriting"（查询改写），是提升召回率的常用手段。

优点：
  - 体验友好，像真人客服
  - 能有效提升问题解决率

缺点：
  - 实现复杂度高
  - 候选问题的质量取决于 LLM

【🔴 策略 5：多轮检索 + 问答澄清】

做法：第一轮检索不到时，反过来问用户问题，澄清意图后再检索。

例子：
  用户："怎么退款？"
  系统："请问您是想了解订单退款流程，还是会员退款政策？"
  用户："订单退款"
  系统：（检索"订单退款"相关内容，给出答案）

这属于"多轮对话 RAG"，更复杂但体验最好。

【🟣 策略 6：兜底到通用大模型（"我不知道但我可以猜"）】

做法：检索不到时，不基于知识库，直接让 LLM 用通用知识回答，
      但明确告诉用户"以下回答来自通用知识，未经过知识库验证"。

优点：
  - 用户体验最好，几乎"有问必答"
  - 适合 ToC 产品，用户期望高

缺点：
  - 可能产生幻觉，答案不一定准确
  - 违背了 RAG 的初衷（基于可信知识回答）
  - 需要明确的免责声明，避免用户误以为是官方答案

很多 ToC 产品会这么做，比如客服机器人：
  - 知识库能回答的 → 用 RAG，标"官方解答"
  - 知识库答不上的 → 用通用模型，标"仅供参考"

【⚡ 策略 7：转人工 / 提交工单】

做法：检索不到时，提供"转人工"或"提交工单"的入口。

这是企业级客服系统的标配：
  - 简单问题 → RAG 自动回答
  - 回答不了 → 转人工坐席
  - 非工作时间 → 提交工单，上班后回复

通常会配合满意度反馈：用户觉得回答不好，可以一键转人工。

【📊 常见组合策略】

真实线上系统通常不是只用一种，而是组合使用：

  基础版（MVP）：策略 1 + 策略 2（双保险）
  进阶版：策略 3 + 策略 4（先给参考，再引导换问法）
  企业版：策略 3 + 策略 4 + 策略 7（能答就答，答不了引导，还不行转人工）
  ToC 版：策略 3 + 策略 6（尽量回答，标清信息来源）

【🎯 决策参考：选哪种策略？】

问自己几个问题：
  1. 答错的代价有多大？
     → 医疗/法律：选策略 1，宁可不答也不能答错
     → 客服/百科：选策略 3/6，用户体验更重要

  2. 用户是谁？
     → 内部员工：策略 1 也能接受
     → 外部客户：至少要有策略 3/4 的引导

  3. 有多少开发资源？
     → 少：策略 1 + 2，先能用
     → 中：加策略 3 + 4，体验提升明显
     → 多：策略 5 + 7，做完整的多轮 + 人工

【💡 当前项目可以怎么改进？】

以现在的代码为基础，可以低成本做的改进：

  1. 去掉代码层的硬拦截，完全交给 LLM + Prompt 判断
     （反正 Prompt 里已经写了"不要编造"的规则）

  2. 加个"低阈值兜底"：
     - 高阈值（如 0.5）没命中 → 用低阈值（如 0.3）再查
     - 低阈值有结果 → 回答开头加"未找到高度相关内容，以下供参考"

  3. 检索不到时给出引导话术，而不是干巴巴的"无法回答"
     比如："抱歉，知识库中暂无相关内容。您可以尝试换个关键词，
           或查看知识库已覆盖的话题：RAG 技术、LangChain 框架..."

这些改动都不大，但用户体验会好很多。

十二、查询改写（Query Rewriting）详解
==========================================================

【是什么】

查询改写就是把用户的原始问题，用 LLM 改写成几个不同表述的"搜索查询"，
然后用这些查询分别去检索，再把结果合并。

简单说：用户问的可能不标准 → 帮他"换个说法"再搜 → 召回率更高。

【为什么要改写】

1. 用户提问太口语化
   - "RAG 是啥？" → 改写为 "RAG 的定义" "检索增强生成是什么"
   - 口语化的表达和知识库中的书面语差异大，向量相似度低

2. 用户的问题太短，关键词不够
   - "文本切块" → 改写为 "文本切分方法" "文本分块技术"
   - 短查询的信息密度低，embedding 区分度差

3. 用户用了同义词 / 不同表述
   - 知识库写的是 "文本切分"，用户问的是 "文本切块" "文本分段"
   - 向量相似度可能不够高，导致排不到前面

4. 用户的问题太长，主题不突出
   - "我想知道在做 RAG 的时候，文档应该怎么切分比较好，
     有哪些常见的切分策略" → 改写为 "RAG 文档切分策略"
   - 长查询会稀释核心关键词，影响检索效果

5. 提升召回率（Recall）
   - 一个查询可能漏了相关文档
   - 多个不同角度的查询，覆盖更全面，漏检的概率更低

一句话：查询改写是提升 RAG 召回率成本最低的手段之一。

【常见改写方式】

1. 同义词替换
   原："怎么用 LangChain" → 改："LangChain 使用方法" "如何使用 LangChain"

2. 关键词提取
   原："RAG 的全称是什么，它有什么用" → 改："RAG 全称" "RAG 用途"

3. 扩写（短 → 长）
   原："文本切分" → 改："文本切分的方法有哪些" "文本切分技术介绍"

4. 缩写展开
   原："RAG 原理" → 改："检索增强生成 RAG 的工作原理"

5. 多角度改写
   同一个问题，从"是什么/为什么/怎么做"等不同角度生成查询

6. HyDE（Hypothetical Document Embedding）
   高级玩法：让 LLM 先"猜"一个答案，用这个答案去检索
   原理：答案的向量和文档的向量更接近，比问题检索效果更好
   适合：答案比较长、问题比较短的场景

【怎么实现】

两种主流方式：

方式 1：用 LLM 生成（灵活，效果好，推荐）
  - 写个 Prompt，让 LLM 输出 N 个改写后的查询
  - 优点：灵活，能理解语义
  - 缺点：多调一次 LLM，增加延迟和成本

方式 2：规则改写（简单，快，但效果有限）
  - 同义词词典替换
  - 增加/去掉停用词
  - 优点：快，不花钱
  - 缺点：效果有限，无法理解语义

当前项目实现的是方式 1（LLM 改写）。

【集成到 RAG 流程的两种策略】

策略 A：检索不到时才改写（保底模式）
  - 先用原始查询检索
  - 有结果 → 直接用
  - 没结果 → 改写后再检索一次
  - 优点：省 token、延迟低
  - 缺点：有结果但结果不好时不会优化

策略 B：每次都改写 + 结果合并（增强模式）
  - 不管原始查询有没有结果，都改写
  - 多个查询分别检索 → 合并去重 → 按分数排序
  - 优点：召回率更高，排序更好
  - 缺点：每次都多调 LLM + 多次检索，成本高

当前项目两种都支持，通过参数控制：
  - enable_query_rewrite=True 开启
  - rewrite_on_empty_only=True （只在空结果时改写 = 策略 A）
  - rewrite_on_empty_only=False（每次都改写合并 = 策略 B）

【合并结果时的注意点】

1. 去重
   不同查询可能检索到同一个文档，不能重复返回
   去重方式：用文档内容 / 文档 ID 做 key

2. 分数归一化
   不同查询的分数基线可能不一样，不能直接比较
   简单处理：保留最高分的那条
   复杂处理：RRF（倒数排名融合）等融合算法

3. 重新排序
   合并后按分数从高到低重新排序
   （有 Reranker 的话可以在这一步再精排）

当前项目的实现：简单去重 + 取最高分 + 重新排序。

【实际效果对比（当前项目实测）】

查询："RAG 是啥？"
  不开改写：命中 4 条（有重复），最高分 0.71
  开改写：  命中 2 条（去重后），最高分 0.85

查询："文本切块有啥方法"
  不开改写：命中 2 条（有重复），最高分 0.59
  开改写：  命中 2 条（去重后），最高分 0.61

结论：
  - 去重效果明显（消除了重复结果）
  - 改写后的查询能找到分数更高的匹配
  - 排序更合理

【代码位置】

  - 改写器：src/rag/query_rewriter.py（QueryRewriter 类）
  - 集成点：src/rag/rag_chain.py（_retrieve_with_rewrite 方法）
  - 开启方式：RAGChain(enable_query_rewrite=True, rewrite_on_empty_only=False)

【使用建议】

1. 先从"只在空结果时改写"开始（rewrite_on_empty_only=True）
   - 成本增加最少
   - 至少能解决"完全搜不到"的问题

2. 效果还不够的话，再开"每次都改写"
   - 成本增加：每次多调一次 LLM + 多 2~3 次检索
   - 效果提升：召回率和排序质量都有提升

3. 改写数量 3 个比较合适
   - 太少：覆盖不够
   - 太多：成本高，重复度也高

4. 结合 Reranker 效果更好
   - 查询改写提升召回
   - Reranker 提升排序精度
   - 两者配合是 RAG 优化的黄金搭档

【和其他优化手段的关系】

  查询改写   → 提升召回率（把相关的都捞出来）
  Reranker   → 提升准确率（把最相关的排前面）
  调阈值     → 控制精度和召回的平衡
  混合检索   → 向量 + 关键词，各取所长

一般优化顺序：
  基础检索 → 调阈值/Chunk → 查询改写 → 混合检索 → Reranker → 多轮澄清

十三、RAG 常见检索方式总结
==========================================================

RAG 的检索环节有很多种方式，各有优劣。了解它们的特点，才能选对、用好。

【一、关键词检索（稀疏检索 / Sparse Retrieval）】

代表算法：BM25、TF-IDF
原理：基于词频和倒排索引，匹配查询和文档中的共同关键词

优点：
  - 精确匹配能力强（专有名词、产品名、人名、数字）
  - 速度快，适合大规模语料
  - 可解释性强（能知道是哪个词匹配上的）
  - 不需要 embedding 模型，不花钱
  - 对中文分词质量依赖较高

缺点：
  - 不理解语义，同义词匹配不上
    （搜"电脑"找不到写"计算机"的文档）
  - 无法处理模糊匹配和语义近似
  - 对口语化、长问句效果差

适用场景：
  - 法律、医疗等专有名词多的领域
  - 用户查询比较规范（关键词式）
  - 对可解释性要求高的场景

Python 实现：rank_bm25 库、elasticsearch、whoosh

【二、向量检索（稠密检索 / Dense Retrieval）】

代表：Chroma、FAISS、Milvus、Pinecone
原理：把文本转成向量，计算向量相似度（余弦、L2 等）

优点：
  - 理解语义，同义词、不同表述也能匹配
  - 支持模糊匹配和语义近似
  - 对口语化、长问句效果好
  - 跨语言检索（中英文向量空间接近时）

缺点：
  - 精确关键词匹配弱（"iPhone 15 Pro"可能和"iPhone 16"更像）
  - 效果严重依赖 embedding 模型质量
  - 可解释性差（不知道为什么匹配上的）
  - 需要向量化成本（API 费用 / 计算资源）
  - 向量库比倒排索引占空间

适用场景：
  - 通用问答、知识库检索
  - 用户提问不规范、口语化
  - 需要语义理解的场景

当前项目用的就是纯向量检索（Chroma + 余弦相似度）。

【三、混合检索（Hybrid Retrieval）】

原理：向量检索 + 关键词检索，两路召回，结果融合

融合方式：
  1. 加权融合（Weighted Fusion）
     向量分数 * alpha + 关键词分数 * (1-alpha)
     alpha 一般取 0.5~0.7（向量权重稍高）

  2. RRF（倒数排名融合，Reciprocal Rank Fusion）
     不看分数，只看排名：score = Σ 1 / (k + rank)
     优点：不需要归一化不同体系的分数
     经验值 k = 60

  3. 学习排序（LTR, Learning to Rank）
     训练一个模型来融合，效果最好但成本最高

优点：
  - 语义匹配 + 精确匹配，两者优点都有
  - 整体效果通常比单一方式好 10~30%
  - 是工业界 RAG 的标配

缺点：
  - 实现更复杂
  - 检索耗时增加（两路召回 + 融合）
  - 需要调权重参数

适用场景：几乎所有生产级 RAG 系统都推荐用混合检索

【四、其他检索方式（了解即可）】

1. 多向量检索（Multi-vector）
   - 一篇文档生成多个向量（标题、摘要、正文各一个）
   - 检索时分别匹配，取最高分
   - 适合长文档、结构化文档

2. 父文档检索（Parent Document）
   - 检索用小块（chunk），返回时返回整个父文档
   - 解决"chunk 太小上下文不足"的问题
   - LangChain 里叫 ParentDocumentRetriever

3. 知识图谱检索
   - 把知识存成图谱（实体 + 关系）
   - 用图查询 + 向量查询结合
   - 适合关系复杂、需要推理的场景

4. 全文检索（Full-text Search）
   - 最原始的字符串匹配
   - 速度快但效果差，一般只作辅助

【怎么选？】

简单决策树：
  - 只是 Demo / MVP → 纯向量检索（简单够用）
  - 生产环境 → 混合检索（标配，效果提升明显）
  - 专有名词特别多 → 混合检索 + 提高关键词权重
  - 语义理解要求高 → 混合检索 + 提高向量权重
  - 特别长的文档 → 混合检索 + 父文档检索

【混合检索的权重怎么调？】

没有标准答案，靠实验：

  1. 先用 alpha=0.7（向量 0.7，关键词 0.3）作为起点
  2. 准备一组测试查询 + 标准答案
  3. 调整 alpha，看哪个值准确率最高
  4. 嫌麻烦就用 RRF，不用调权重

经验值：
  - 中文场景：向量权重 0.6~0.7 通常比较好
  - 英文场景：向量权重 0.7~0.8 通常更好
  - 专有名词多：关键词权重适当提高

【和其他优化手段的关系图】

  ┌─────────────────────────────────────────────┐
  │              召回层（Recall）                │
  │  向量检索 ←→ 关键词检索 ←→ 查询改写         │
  │  （语义匹配） （精确匹配） （多角度覆盖）    │
  └──────────────────────┬──────────────────────┘
                         │
              混合检索 / 结果融合
                         │
  ┌──────────────────────▼──────────────────────┐
  │              精排层（Precision）             │
  │  Reranker（重排序） → 阈值过滤               │
  └──────────────────────┬──────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────┐
  │              生成层（Generation）            │
  │  Prompt 构建 → LLM 生成回答                 │
  └─────────────────────────────────────────────┘

一句话：召回层负责"把相关的都捞出来"，
       精排层负责"把最相关的排前面"，
       生成层负责"用通顺的话回答用户"。

十四、实际开发中配置项怎么写？写在哪里？
==========================================================

【核心原则】配置分三层，各司其职：

  代码默认值（settings.py） → 环境变量（.env） → 运行时动态调整（前端/API）

每一层都可以覆盖上一层的值，越往后优先级越高。

【第一层：代码默认值 → config/settings.py】

放什么：
  - 所有配置项的字段定义 + 默认值
  - 非敏感配置（chunk_size、top_k、开关等）的合理默认值
  - 敏感配置的默认值设为空字符串（""），不要填真实密钥

为什么放这里：
  - 是配置的"单一真相来源"，所有配置项都在这里声明
  - 有类型提示（pydantic），写错类型会报错
  - 有默认值的配置项可以直接用，不用每次都在 .env 里写
  - 新人看这个文件就知道项目有哪些配置

命名规范：
  - Python 字段名：小写 + 下划线（snake_case）
    例：llm_api_key、enable_rerank、chunk_size
  - 自动对应环境变量：全大写（UPPER_SNAKE_CASE）
    例：LLM_API_KEY、ENABLE_RERANK、CHUNK_SIZE

【第二层：环境变量 → .env 文件 + .env.example】

.env 文件放什么：
  - 敏感信息（API Key、密码、Token 等）——必须放这里，不能提交
  - 部署环境特有的值（比如生产环境的 LLM 模型名、向量库路径）
  - 覆盖 settings.py 默认值的配置

.env.example 文件放什么：
  - 所有配置项的模板，值用占位符（如 your-api-key）或默认值
  - 有注释说明每个配置的作用和可选值
  - 这是配置文档，新人拿到项目看这个文件就知道怎么配置

为什么需要 .env.example：
  - .env 不提交（.gitignore 里排除），别人拉代码不知道要配置什么
  - .env.example 提交到 git，作为配置清单和模板
  - 使用方式：cp .env.example .env，然后填入真实值

.env 书写规范：
  - 变量名全大写 + 下划线
  - KEY=VALUE 格式，等号两边不要有空格
  - 值有特殊字符（空格、引号等）时加双引号
  - # 开头是注释

【第三层：运行时动态调整 → 前端参数面板 / API】

放什么：
  - 需要频繁调整、调优的参数（top_k、阈值、开关等）
  - 不涉及密钥和基础设施的配置

为什么需要：
  - 调参不用改代码、不用重启服务
  - 产品/运营人员也能操作
  - 做 A/B 测试方便

【配置分层的实际例子（以 Rerank 为例）】

  settings.py 中定义：
    enable_rerank: bool = False          ← 默认关闭
    rerank_model: str = "gte-rerank-v2"  ← 默认模型
    rerank_top_n: int = 3                ← 默认返回 3 条

  .env 中覆盖（部署级）：
    ENABLE_RERANK=true                   ← 这个环境默认开启
    RERANK_API_KEY=sk-xxx                ← 敏感信息，放这里

  前端面板（运行时）：
    用户可以随时开关 Rerank、调整 top_n ← 运行时动态调整

【配置项的命名建议】

  1. 布尔开关用 enable_ / is_ / has_ 开头
     例：enable_rerank、enable_hybrid_search、is_production

  2. 同类配置用统一的前缀
     例：llm_xxx、embedding_xxx、rerank_xxx
     好处：一眼就知道属于哪个模块，排序后聚在一起

  3. 数量/大小用 _size / _count / _num 后缀
     例：chunk_size、top_k、max_tokens

  4. 阈值用 _threshold 后缀
     例：similarity_threshold、rerank_threshold

  5. 路径用 _path / _dir 后缀
     例：vector_db_path、documents_dir

【常见误区】

  ❌ 误区 1：把 API Key 直接写在 settings.py 里
     → 泄露风险！settings.py 会提交到 git

  ❌ 误区 2：配置项散落在代码各处，没有统一管理
     → 维护噩梦，改配置要翻遍整个代码

  ❌ 误区 3：.env.example 不更新，加了新配置别人不知道
     → 加新配置时，记得同步更新 .env.example

  ❌ 误区 4：配置名随意，一会儿 camelCase 一会儿 snake_case
     → 容易拼错、找不到，统一风格很重要

  ✅ 正确做法：
     所有配置 → 在 settings.py 声明
     敏感/环境特有 → .env 覆盖
     配置模板 → .env.example 同步更新
     需要动态调 → 前端/API 暴露参数

  配置定义：    config/settings.py   （pydantic-settings，已提交）
  环境变量：    .env                 （真实密钥，不提交）
  配置模板：    .env.example         （模板 + 注释，已提交）
  运行时调整：  web/gradio_app/app.py 左侧参数面板
